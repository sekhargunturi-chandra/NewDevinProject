Welcome to the Intelligent Payment Fraud Investigation and Dispute Resolution Agent. I will walk you through the complete flow.
Step one. Health check. The application is running on port eighty eighty-one. The login page responds with HTTP two hundred, so the service is alive.
Step two. Case intake. An agent submits a fraud case through the REST API. The customer reports an online purchase from a merchant they do not recognise, made from a new device and an unusual location. The card is still in the customer's possession. The system returns a generated case ID in state NEW.
Step three. Input validation. A deliberately incomplete request is rejected with HTTP four hundred and field-level errors. Masked references and mandatory fields are enforced before any case is created.
Step four. Case read-back. The case is fetched and confirmed to be in state NEW. This is the only state from which an investigation can begin.
Step five. Investigation. An investigator triggers the investigation. The orchestrator moves the case to ENRICHING, runs the allow-listed deterministic evidence tools under a timeout, retrieves matching policy clauses, and calls the active processor. In this demo the recommendation is UNAUTHORISED TRANSACTION, risk HIGH, routed to FRAUD INVESTIGATION, with confidence zero point eight five. The missing authentication outcome is reported under missing information, never invented.
Step six. Tool trace. Eight tool invocations are recorded, each with status, duration and a trace ID. This gives the analyst full observability of what evidence was collected.
Step seven. Evidence workspace. Every evidence item shows its type, severity and provenance. Device and merchant signals came back HIGH severity, which is why the multi-anomaly rule fired.
Step eight and nine. Recommendation and policy citations. The persisted recommendation shows which processor mode produced it. Each citation carries document ID, version, section, chunk ID and similarity score. If nothing clears the threshold, the assistant abstains instead of guessing.
Step ten. Case-scoped memory. A follow-up question gets a case-aware answer. A different case gets an independent context. Memory never leaks between cases.
Steps eleven to thirteen. Human review. A disposition without a rationale is rejected. A non-reviewer role is forbidden. A reviewer with a rationale accepts the recommendation, and the case moves from UNDER REVIEW to ROUTED.
Step fourteen. State machine guard. Re-investigating a routed case is rejected with HTTP four zero nine. Illegal transitions cannot happen.
Step fifteen. Audit trail. The append-only log reconstructs the entire journey: case created, status transitions, recommendation persisted by the model, the follow-up question, and the reviewer's acceptance. Only payload hashes are stored, never raw sensitive data.
Step sixteen. A second scenario proves the decision is evidence-driven. A duplicate-processing case routes to PAYMENT OPERATIONS instead.
Step seventeen. That is the complete flow. The assistant only recommends routes. It never blocks a card, issues a refund, moves funds, files a report or contacts a customer. A human reviewer always makes the final call.
